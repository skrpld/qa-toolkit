# nvme-iops-bench

Офлайн-набор для дисковых проверок ВМ: статически собранный `fio` плюс обвязка,
упакованные в один ISO. Рассчитано на ситуацию, когда на рабочей машине нельзя ставить
софт, а целевая VM без интернета — всё собирается на раннере GitHub и приезжает образом.

Изначально инструмент делался под одну задачу — проверить, отдаёт ли провайдер заявленные
в тарифе IOPS. Но на ISO лежит полноценный `fio`, поэтому им же закрываются и остальные
дисковые сценарии, без отдельных скриптов.

## Сценарии

| Сценарий | Чем делается | Раздел |
| --- | --- | --- |
| Проверить тарифные IOPS: серия из десяти профилей + сводная таблица | `run_benchmark.sh` + `generate_report.py` | [Полный прогон](#полный-прогон-iops-по-тарифу) |
| Забить диск данными: N файлов заданного размера или ФС до отказа | `fio` напрямую | [Заполнение диска](#заполнение-диска-данными) |
| Разовая проверка одного профиля: латентность, полоса, конкретная QD | `fio` напрямую | [Точечные проверки](#точечные-проверки) |
| Проверить, что записанное читается без искажений | `fio --verify` | [Проверка целостности](#проверка-целостности-данных) |
| Выяснить, есть ли burst-кредиты и когда они кончаются | `run_benchmark.sh` с разным `RUNTIME` | [Как читать цифры](#как-читать-цифры) |

## Из чего состоит

| Файл | Роль |
| --- | --- |
| `.github/workflows/build-nvme-iops-bench-iso.yml` | собирает статический `fio` и упаковывает его вместе со скриптами в ISO |
| `run_benchmark.sh` | гоняет серию тестов, складывает сырые json от fio |
| `generate_report.py` | сводит json в markdown-таблицу |
| `bin/fio` (на ISO) | сам fio; доступен напрямую для всего, что не покрыто скриптами |

Workflow лежит в корне репозитория (`.github/workflows/`), а не в этой папке —
GitHub Actions видит только workflow-файлы под корневым `.github/workflows/`.

## Сборка ISO

Запускается вручную: вкладка **Actions** → workflow **Build offline nvme-iops-bench ISO** → **Run workflow**. Поле `fio_version` позволяет собрать другой тег fio, по умолчанию `fio-3.36`.

Готовый образ лежит в блоке **Artifacts** завершившегося run'а — `nvme-iops-bench-iso.zip`,
внутри `nvme-iops-bench.iso`.

Если сборка упала, смотреть по шагам:

- **Expose kernel and libaio headers/libs** — `musl-gcc` подменяет пути поиска заголовков и
библиотек своими, поэтому заголовки ядра и libaio прокидываются симлинками. Падение
`test -e` здесь означает, что пакет не встал или путь в дистрибутиве переехал.
- **Preflight** — минимальная программа, линкующаяся с libaio через musl. Ловит проблемы
линковки до того, как они превратятся в невнятное `Linux AIO support no` в выводе configure.
- **Build static fio** — после configure стоят два гейта: сборка должна быть статической и с
libaio. Без них получился бы ISO, который падает уже на офлайн-VM. При провале гейта в лог
выводится хвост `config.log`.
- **Verify binary** — `file`/`ldd` подтверждают статику, `--enghelp` показывает, какие
ioengine реально доступны.

## Подготовка на ВМ

ISO монтируется штатно (`mount /dev/sr0 /mnt/cdrom`). Ставить на VM ничего не нужно:
скрипт находит `bin/fio` рядом с собой, а для запуска fio вручную достаточно вызвать
`/mnt/cdrom/bin/fio`. Из внешних зависимостей остаётся только `python3` — и только для
генерации отчёта.

Если ISO смонтирован без бита выполнения, скрипты запускаются через `bash run_benchmark.sh`.
Результаты писать на CD-ROM нельзя, он read-only — все выходные пути должны указывать
куда-то на диск ВМ.

## Выбор цели

Все сценарии ниже принимают либо путь к файлу на смонтированной ФС, либо сырое блочное
устройство. Разница принципиальная: **работа с блочным устройством уничтожает все данные
на нём целиком**, включая таблицу разделов.

Системный диск исключается вручную: `findmnt -n -o SOURCE /` даёт корневой раздел,
`lsblk -no PKNAME <раздел>` — диск, которому он принадлежит. Всё остальное из `lsblk -d` —
кандидаты.

Безопаснее вообще не трогать сырое устройство: если на нецелевом диске есть смонтированная
ФС, достаточно передать путь к файлу на ней. Цифры при этом чуть ниже, чем на raw-устройстве,
но профиль нагрузки тот же. Для проверки тарифа этой точности хватает.

## Полный прогон: IOPS по тарифу

```
./run_benchmark.sh <TARGET> [SIZE] [OUTDIR]
```

`TARGET` — файл или блочное устройство. Для устройства скрипт запросит подтверждение `yes`.
`SIZE` (по умолчанию 4G) применяется только к файлу. Прогон занимает `RUNTIME + RAMP_TIME`
секунд на каждый из десяти под-тестов — по умолчанию около шести минут.

Переменные окружения:

| Переменная  | По умолчанию | Смысл                                                           |
| ----------- | ------------ | --------------------------------------------------------------- |
| `RUNTIME`   | `30`         | секунд на под-тест; меньше 30 даёт шумные цифры на burst-дисках |
| `RAMP_TIME` | `5`          | прогрев, не попадающий в статистику                             |
| `IOENGINE`  | автовыбор    | `libaio` → `io_uring` → `psync`                                 |

Автовыбор нужен потому, что `io_uring` требует ядра 5.1+, а состав движков зависит от того,
как собрался fio. На синхронном движке (`psync`) `iodepth` игнорируется — все результаты при
QD>1 будут занижены, скрипт об этом предупреждает в начале прогона.

Результаты по умолчанию пишутся в `/var/tmp/nvme-iops-bench/<timestamp>/`, а не рядом со
скриптом: CD-ROM смонтирован read-only. Путь последнего прогона остаётся в `/tmp/nvme_bench_last_outdir`.

### Отчёт

`generate_report.py <OUTDIR>` собирает markdown-таблицу и кладёт её в `report.md` внутри
того же каталога. Сырые json от fio остаются на месте — в них на порядок больше данных
(перцентили, распределение latency, поведение по времени), если понадобится копать глубже.

### Как читать цифры

Провайдеры гарантируют IOPS на блоке 4k и при определённой глубине очереди, поэтому
сравнивать заявленное значение нужно со строкой той же QD, а не с максимумом по таблице.
Строки `randread_4k_qd*` и `randwrite_4k_qd*` показывают, где именно упирается диск: если
IOPS перестаёт расти с QD 32 на 64, лимит достигнут; если растёт линейно — упор в глубину
очереди, а не в диск.

`randrw_70r30w_4k_qd32` ближе всего к тому, что реально считается в биллинге: смешанный
профиль обычно даёт заметно меньше, чем чистое чтение.

`latency_4k_qd1` показывает задержку без очереди. Расхождение между средней и p99 — главный
индикатор соседей по хосту: у выделенного локального NVMe они близки, у сетевого или
переподписанного диска p99 уходит в разы выше.

`seqread_128k` / `seqwrite_128k` даны для справки. Последовательная нагрузка упирается в
пропускную способность, а не в IOPS, и с тарифными цифрами по IOPS не сопоставляется.

Отдельно стоит учитывать burst-кредиты: многие тарифы держат высокие IOPS первые десятки
секунд, а затем срезают до базового уровня. Если цифры при `RUNTIME=30` заметно выше, чем
при `RUNTIME=300`, — это он.

## Заполнение диска данными

Отдельный скрипт для «забить место» не нужен: fio реально пишет данные, а не преаллоцирует
экстенты, поэтому sparse-файлов не возникает в принципе.

Сто файлов по 10 МБ в каталоге:

```
/mnt/cdrom/bin/fio --name=fill --directory=/mnt/data --rw=write --bs=1M \
                   --nrfiles=100 --filesize=10M --unlink=0
```

Забить ФС до отказа (fio пишет, пока не упрётся в ENOSPC):

```
/mnt/cdrom/bin/fio --name=fill --directory=/mnt/data --rw=write --bs=1M \
                   --fill_device=1 --unlink=0
```

| Флаг | Зачем |
| --- | --- |
| `--unlink=0` | значение по умолчанию, указано явно: иначе легко случайно включить удаление файлов после прогона |
| `--zero_buffers` | писать нули вместо случайных данных |
| `--buffer_compress_percentage=50` | частично сжимаемые данные — когда проверяется именно сжатие на стороне хранилища |

По умолчанию буферы случайные, то есть дедупликация и компрессия на стороне СХД место не
«съедят» — это то поведение, которое обычно и нужно при проверке квот и алертов на
заполнение.

## Точечные проверки

Когда нужен один профиль, а не вся серия. Общая форма — `--time_based` плюс `--runtime`,
иначе fio остановится, пройдя `--size` один раз.

Латентность без очереди (тот же профиль, что `latency_4k_qd1` в полном прогоне):

```
/mnt/cdrom/bin/fio --name=lat --filename=/mnt/data/testfile --size=1G \
                   --rw=randread --bs=4k --iodepth=1 --ioengine=psync \
                   --runtime=30 --time_based
```

Полоса на последовательном чтении:

```
/mnt/cdrom/bin/fio --name=bw --filename=/mnt/data/testfile --size=4G \
                   --rw=read --bs=1M --iodepth=32 --ioengine=libaio \
                   --runtime=30 --time_based
```

Конкретная глубина очереди на случайной записи — подставить нужное `--iodepth`:

```
/mnt/cdrom/bin/fio --name=qd --filename=/mnt/data/testfile --size=4G \
                   --rw=randwrite --bs=4k --iodepth=64 --ioengine=libaio \
                   --runtime=30 --time_based
```

Если `libaio` в сборке нет или ядро старое — `/mnt/cdrom/bin/fio --enghelp` покажет
доступные движки. На `psync` любые значения `--iodepth` игнорируются.

## Проверка целостности данных

Записать и перечитать с контрольными суммами — ловит молчаливую порчу данных на тонких
томах, сетевых дисках и после миграций ВМ:

```
/mnt/cdrom/bin/fio --name=verify --filename=/mnt/data/testfile --size=1G \
                   --rw=write --bs=1M --verify=crc32c --do_verify=1 \
                   --verify_fatal=1
```

`--verify_fatal=1` останавливает прогон на первом расхождении, иначе fio досчитает до конца
и ошибку легко пропустить в выводе. Ненулевой код возврата = данные не совпали.
